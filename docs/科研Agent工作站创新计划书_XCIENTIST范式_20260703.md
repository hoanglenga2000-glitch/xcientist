# 面向机器学习研究的经验驱动型 AI Scientist

## 以可审计的"选点—晋升—修复"契约过程，支撑持续实验与经验积累

**作者**：景浩伟  ·  **日期**：2026-07-03  ·  **状态**：研究闭环已在中小规模任务上跑通，核心机制已在真实 A40 GPU 端到端验证

---

## 摘要

本计划的目标不是再造一个"更能刷分"的 Kaggle / MLE-Bench Agent，而是构建一个**面向机器学习研究的经验驱动型 AI Scientist**——让 AI 像研究员一样完成完整的研究循环：**发现问题、提出假设、设计实验、验证结果、分析失败、总结经验，再基于经验提出下一轮更好的假设**。我的核心判断是：真正有效乃至具有创新性的方法极少是一次性生成的；人类研究员也要经过大量实验、失败、归因与修正才逼近有效解。因此系统最核心的思想是**让 AI 在持续实验中积累经验、从量变逐步逼近质变**。在这个定位下，Kaggle / MLE-Bench 不是最终目标，而是一个**真实、复杂、可量化反馈的实验场**；真正重要的不是最终拿没拿到名次，而是这个研究闭环能否成立、研究过程的质量能否持续提升。

当一个研究循环要跑满数百步实验预算、并让"经验"真正驱动后续假设时，一个新的基础问题就凸显出来：**这些中间判断必须可被检查，否则经验无从积累**。为什么扩展这个节点而不是那个、一个候选凭什么晋升为新基线、一次失败到底错在哪——现有自动化系统（AutoKaggle、Agent K、MLEvolve 等）里，这些决策往往被埋在一次性提示、临时脚本和不透明的模型推理里，事后无法追溯。一个被误判为成功的失败运行会污染后续所有以它为基线的比较，一次被截断的报错会让"失败归因"沦为盲猜——经验一旦建立在错误判断上，量变就永远到不了质变。所以本计划把研究循环中三类关键判断——**选点、晋升、修复**——外化为显式的、有契约约束、可审计的机制，让每一次实验的经验都建立在可检查的证据之上。在实现这套机制的过程中，我诊断并修复了现有开源方案（MLEvolve）中三处真实的、会导致机制失效的缺陷：

1. **方向正确、有测试的 MCGS 选点大脑**（`mcgs_selector.py`，263 行）。诊断出被广泛参考的 MLEvolve UCT 实现实际上**不可用**——`visit_count` 声明并读取却从不自增，选点退化为"永远选第一个孩子"，且对 minimize 指标方向算反。我不桥接这份负债，而是把它的健全设计移植成一份**写对且有 9 条离线测试**的独立实现。
2. **单分支自举的死锁修复**。诊断出旧扩展逻辑存在"要有第二分支才能建第二分支"的循环依赖，使真实单任务永远塌成一条深链，跨分支融合成为**够不到的死代码**。我引入主动 DIVERSIFY 机制打破死锁——并在真实 GPU 上验证：它开出的分支产出了**全局最佳解**。
3. **晋升门禁的 `run_success` 硬前置**。诊断出"失败但产物已落盘"漏洞——远程 GPU 进程被 kill 前已把合法分数刷到盘，旧门禁只看"分数+产物"便误晋升。修复后，非零退出的运行一律不可晋升。
4. **可观测的修复闭环**。诊断出失败自愈"蒙着眼"——真 traceback 被 torch.hub 下载进度条挤掉，循环只把 120 字符摘要喂回修复提示。修复后剥离进度帧、落盘完整报错、把真错误喂回修复。

这四项都不是概念方案。它们全部有回归测试锁定，并在真实 A40 GPU（job 87907，Opus 4.8 全程）上端到端复验。系统以**终端式工具**交付（可全局安装、本地初始化、配置自有大模型/Kaggle API、可选远程或本地算力），前端面板作为辅助 dashboard 展示实验进度、搜索树与经验总结。受限于单张 A40 与 MLE-Bench 的数据规模，本计划**有意先在可复现、可下载、数据规模适中的任务上验证研究闭环是否成立**，而非追逐排行榜名次。本计划的立场是：**AI 研究的价值不在于"跑出一个结果"，而在于让从证据到结论的每一步都可被外部检查与追责、让经验可被复用**——这正是把它与"又一个自动打比赛的脚本"区分开的地方。

## 一、引言

近年的自动化数据科学系统已经展示了很强的端到端能力：AutoKaggle 把竞赛拆成阶段化流程并设置多角色分工；Agent K 引入 scaffold 与 post-scaffold 迭代；MLEvolve 用渐进式蒙特卡洛图搜索（Progressive MCGS）在多任务基准上取得了很强的端到端表现。它们证明了 Agent 能生成想法、写代码、跑实验，也把 medal rate、模型搜索、memory、resume、dashboard 等能力推到了很高的水平。这些能力都很重要，也确实是本系统需要具备的**基础能力**。

**但本计划想突出的创新不是再做一个"会刷分的 Agent"，而是做一个面向机器学习研究的经验驱动型 AI Scientist。** 二者的区别在于评价对象：前者关心"最终分数高不高"，后者关心"研究过程本身像不像一个研究员、并且能不能越做越好"。我的核心判断是——**创新极少是一次性生成的**。人类研究员也不是一上来就提出一个有效的新算法，而是经过大量实验、失败、归因、总结，不断修正假设，才逐渐逼近真正有效的方法。所以这个系统最核心的思想是：**让 AI 在持续实验中积累经验，通过大量失败与总结形成更高质量的研究判断，从量变逐渐走向质变**。在这个意义上，Kaggle / MLE-Bench 对我不是终点，而是一个**真实、复杂、可量化反馈的实验场**——它提供了一个能持续给出客观信号、让"经验积累是否真的在起作用"变得可测量的环境。

而一旦把目标从"刷分"换成"让经验驱动研究"，科学研究最古老的那条要求就重新变得关键：**推理链必须可被检查**。一个结果之所以有科研价值，是因为它可追溯、可复现、可控制、可被他人质疑。当这些判断被交给自动化系统、并且要**沉淀为下一轮实验所依赖的经验**时，这个要求不但没有消失，反而更难满足——因为经验一旦建立在无法检查的判断上，错误就会被继承和放大。可现有系统的**中间判断仍然难以审计**：选点为什么这样选、晋升凭什么晋升、一次失败到底错在哪——这些决策要么散落在一次性提示里，要么被埋进模型权重，事后无从追溯。

这个局限并非细枝末节。在一个跑满数百步搜索预算的进化循环里，**一个隐式的错误判断会被放大成整条错误的搜索轨迹**：一次被误判为成功的失败运行，会污染后续所有以它为基线的比较；一个够不到的融合分支，会让系统在最该整合多路方案时反而塌成一条深链。因此，真正的挑战不是"自动化更多的科研步骤"，而是**让自动化的科研判断变得可被外部治理**。

本计划的核心主张是：把研究循环里的三类关键判断——**该扩展哪个节点（选点）、一个候选能否成为新基线（晋升）、一次失败该如何被诊断（修复）**——从"藏在推理里的自由裁量"改造成"有契约约束的显式过程"。这三类判断恰好对应研究循环里"提出假设→验证→失败归因→再提出"的关节：选点决定下一个假设从哪里长出来，晋升决定哪些结果值得沉淀为新基线，修复决定失败能否被准确归因并反哺下一轮。每一步都必须产出可检查的证据（选点计划、晋升裁决、清洗后的报错、validation/claim 审计），循环才能继续——也只有这样，"经验"才不是一句口号，而是可被复用、可被质疑的东西。

我在做这件事的过程中，对被广泛参考的开源实现 MLEvolve 做了工程逆向，发现它的 MCGS "大脑"虽然设计思路健全，但**核心 UCT 不可用**、且存在若干会导致机制失效的缺陷。本计划不选择"把这份负债跨包桥接进来"，而是**诊断根因、移植健全设计、写出正确且有测试的独立实现**，并在真实 GPU 上验证这些修复不只是"测试通过"，而是"在真实硬件上改变了搜索结果、并收敛到了全局最优解"。这构成了本计划区别于单纯复刻的**自研技术贡献**。

## 二、经验驱动的研究循环：从"刷分"到"像研究员一样工作"

本计划把 AI Scientist 要走的路径显式建模为一个**研究循环**，而不是一次性的"读题→写代码→提交"：

```
发现问题 → 提出假设 → 设计实验 → 运行/验证 → 分析失败与归因 → 总结经验(memory)
                    ↑                                              │
                    └──────────── 基于经验提出更好的下一轮假设 ──────┘
```

这个循环与后文的工程部件是一一对应的，不是修辞：

| 研究循环的一环 | 系统里的落地部件 | 产出的可检查证据 |
|---|---|---|
| 提出假设、决定从哪深入 | **选点大脑**（MCGS selector） | `ExpansionPlan`（node/type/mode/references） |
| 设计并生成实验 | **变体生成器** | 满足契约的解题脚本 + 契约声明 |
| 验证结果能否沉淀为基线 | **晋升门禁** | `validation_contract.json` + 晋升 reason |
| 分析失败、准确归因 | **可观测修复闭环** | `run_error.txt`（清洗后的真 traceback） |
| 总结经验、反哺下一轮 | **回顾式记忆**（lessons/memory） | 跨任务复用的 `lessons` 注入下一次提示 |

**为什么把"经验积累"当作一等公民。** 单次实验的好坏有很强的偶然性；但如果一个系统能把"这次为什么失败、下次该避免什么、哪类任务上什么策略有效"沉淀成可复用、可检查的经验，那么它在足够多的实验之后，就有机会从"碰运气"走向"有判断"。这正是量变到质变的通道。而这条通道成立的前提，就是**每一步判断都可被追溯**——否则积累起来的可能是错误经验，越积越偏。

**评价对象因此从"分数"转向"研究过程的质量"。** 本计划真正关心、并希望被评价的是：

- **假设是否合理**：提出的下一步是否有据（领域洞见/CV 历史/记忆），而非随机试。
- **实验设计是否真能验证问题**：CV 方案、验证集设计是否与任务匹配，能否把假设证伪。
- **失败归因是否准确**：拿到的是不是真错误（而非被进度条噪声淹没的假象），归因是否指向根因。
- **经验是否被复用**：先前任务学到的教训有没有被后续实验真正调用（已有测试锁定跨任务记忆注入）。
- **方法是否在进化**：能否从简单调参，逐步发展到更有任务针对性的验证集设计、loss 设计、数据增强、后处理、伪标签、ensemble 等更高阶手段。

这些维度都比"最终名次"更能反映一个 AI Scientist 是否真的在"做研究"。它们也天然要求过程可审计——这就把本计划的立意（经验驱动）与方法（可审计的选点—晋升—修复契约）接在了一起。

## 三、系统架构概览

系统的骨架是一个**结果驱动的闭环进化引擎**，它把工作站从早期"固定三步流水线"升级为可以跑满预算的搜索循环：

```
seed baseline → 运行 → 打分 → 晋升门禁 → 记教训 → 用历史+记忆+选点大脑提出下一个变体 → 重复
```

早期系统缺的正是"提出变体"这一步（靠 `if n_prev==0/1/2` 硬编码模式切换）。现在这一步由三个可检查的部件协同完成，每个部件都对应一个持久化的研究工件：

| 部件 | 文件 | 职责 | 产出的可检查工件 |
|---|---|---|---|
| **选点大脑** | `mcgs_selector.py` (263 行) | 决定扩展哪个节点、用哪种扩展类型、哪种编码模式 | `ExpansionPlan`（node/type/mode/references/phase） |
| **变体生成器** | `variation_generator.py` (424 行) | 把任务上下文+CV历史+记忆教训+策略交给 LLM 生成满足契约的可运行脚本 | 解题脚本 + 契约声明 |
| **循环编排** | `evolution_loop.py` (564 行) | 晋升门禁、停滞转 Diff、写记忆、Runner 可插拔 | 每实验 `validation_contract.json` + `claim_audit.json` |
| **搜索图** | `search_graph.py` (301 行) | 审计级节点血缘、方向感知的晋升裁决 | `research_os_search_graph.json` + 晋升 reason |

**Runner 抽象是双轨合一的关键**。`LocalSubprocessRunner` 和 `GPURunner` 实现同一个 `Runner` 协议，因此本地与真实 A40 GPU 用**完全相同**的循环逻辑。这把历史上分裂的"本地 mock 轨"和"真 GPU 轨"合成一条，保证了在本地写对、有测试的机制，到 GPU 上跑的是同一套代码。

**证据基底贯穿全程**。每个实验产出 `validation_contract.json`（该实验声明的基线、指标、验证方案）与 `claim_audit.json`（真实检测 claim drift，不是橡皮图章）。这两个工件源自 `research_os` 库、非内联复刻，是"从证据到结论可追溯"这一主张的落地。

架构的设计原则是**只读审计、私有侧表**：选点大脑只读搜索图，把 visit/branch/停滞等中间状态全放在私有 side-table 里，对搜索图那份**被审计的节点 schema 零改动**。这样即使选点逻辑演化，节点血缘的审计契约也不会被污染。

## 四、被外化的失败模式

XCIENTIST 把"claim drift"（可运行工件不再支持最初宣称的机制）识别为自动化研究的一种失败模式。沿着同样的思路，本计划在结果驱动进化引擎里识别并外化了**四种此前隐式、会导致机制失效的失败模式**。它们不是假想的——每一种都是我在工程逆向或离线 trace 复现中真实发现的。

**失败模式 A：失败但产物已落盘（false promotion）。** 远程 GPU 进程在被 kill（OOM/超时）前，可能已经把一个合法的 `CV_SCORE=` 和 `submission.csv` 刷到了磁盘。旧晋升门禁只检查"分数存在 + 产物存在"，于是把一次**实际崩溃的运行**误判为成功并晋升为新基线。之后所有以它为基线的比较全部被污染。

**失败模式 B：单分支自举死锁（unreachable fusion）。** 旧扩展逻辑里，aggregation（融合）要求 `≥2 个分支`、cross_branch 要求"别的分支有更优解"，而**只有这两条路会新建分支**——于是形成"要有第二分支才能建第二分支"的循环依赖。真实单任务因此永远塌成一条 `intra_branch` 深链，跨分支融合是**够不到的死代码**。旧单测靠手工注入两个分支才"通过"，从未测过系统能否**自发**到达多分支。

**失败模式 C：蒙着眼的修复（blind repair）。** 失败运行的完整报错从不落盘，循环只把 `note[:120]` 喂回 Diff 修复提示。而一个真实案例中（aerial-cactus EXP001），那 120 字符里装的其实是一条 `torch.hub` 下载进度条，**真正的 traceback 被进度帧挤掉了**。修复提示因此看不到真错误，自愈形同盲猜。

**失败模式 D：全局停滞被误当作停止信号。** 旧循环的全局停滞会无条件 `break`。但对一个具备融合能力的搜索引擎而言，全局停滞恰恰是**触发跨分支/融合的信号**，而不是停止的理由。旧逻辑会在系统最该融合多路方案时把循环杀掉。

这四种失败模式的共同点是：**它们都源于把一个本该显式、有契约约束的判断，留给了隐式的默认行为**。下一节的四项创新，正是把这些判断逐一外化。

## 五、核心创新与自研技术

### 创新一：方向正确、有测试的 MCGS 选点大脑

**根因诊断。** 工作站中层历史上存在"两套搜索"：工作站自带的 `strategy/mlevolve_search.py` 有 UCT 树的"大脑"却不接真实执行；新引擎 `evolution_loop` 有真实执行的"手"却只有线性 best-so-far。我对前者做深审后确认它**不可用**：

- `visit_count` 被声明、被读取，却**从不自增**。于是 `_uct_value` 永远命中 `visits==0 → +inf` 分支，选点退化为"永远选第一个孩子"——UCT 从未真正生效。
- exploitation 项用 `score / visits`，这对 minimize 方向（如 RMSLE、log loss）是**算反的**。
- 零测试。

**为什么不桥接。** 直接 import 这份实现会跨包继承一个不可用的 UCT、还会引入第二个 `SearchGraph` 名字冲突。我的选择是：**移植它健全的设计思想，写一份正确且有测试的独立实现**，操作工作站自己的搜索图。

**自研实现（`mcgs_selector.py`，263 行）。**
- **方向正确的 UCT**：exploitation 用归一化 reward（复用搜索图的 `_is_better` / `_node_score`），maximize 与 minimize 都对；未访问节点返回 `+inf`，保证每个孩子先各试一次。
- **backpropagate 真正沿父链自增 `visit_count`**——UCT 第一次真正活起来。
- **四种扩展类型**：`primary`（主扩展）/ `intra_branch`（分支内深化）/ `cross_branch`（分支停滞→借其它分支高分方案）/ `aggregation`（全局停滞→融合 top 节点）。
- **渐进探索调度**：探索常数 C 从 1.414 分段衰减到 0.5（早期平探索、中期线性衰减、后期封底），并**按调用方的真实预算缩放**（不像旧实现硬编码 500 步）。
- **只读搜索图**：visit/branch/停滞全在私有 side-table，被审计的节点 schema 零改动。
- **优雅降级**：selector 任何异常都回退为线性选点，绝不崩掉主循环。
- **测试**：9 条选点级离线确定性测试，覆盖冷启动到达多分支、diversify 桥、封顶等。

选点大脑接入 `evolution_loop` 是 **opt-in（默认关，`--mcgs` 开关）**：`select → propose → run → gate → backpropagate`。`VariationGenerator` 相应新增 `expansion_type` / `reference_solutions`，cross/aggregation 会把参考代码注入生成提示。

### 创新二：单分支自举的 DIVERSIFY 死锁修复

**根因诊断。** 见失败模式 B——"要有第二分支才能建第二分支"的循环依赖，使 cross/aggregation 成为够不到的死代码。这是落地 MCGS 后我用离线 trace 逐步复现才暴露的缺陷，旧单测因为手工注入了两个分支而从未触及。

**自研修复。** 当一个分支停滞、但当前无处可借（没有别的分支）时，选点大脑**主动 DIVERSIFY**：从全局最优另开一个新分支自举。此后 cross_branch / aggregation 才第一次变得可达。新分支受 `max_branches` 封顶，不会失控。新增 3 条测试锁定：diversify 桥、封顶、冷启动端到端到达多分支并触发 aggregation。

**这一修复的份量**在验证章会给出——它开出的分支在真实 GPU 上**产出了全局最佳解**。

### 创新三：晋升门禁的 `run_success` 硬前置

**根因诊断。** 见失败模式 A——"失败但产物已落盘"。

**自研修复（`search_graph.py::decide_promotion`）。** 晋升门禁新增 `run_success` **硬前置条件**：一个候选只有在同时满足 (1) 运行成功完成、(2) 分数在声明的指标方向上有改善、(3) 必需证据工件存在时，才可晋升。非零退出（崩溃/OOM/超时）一律不可晋升，即便它在死亡前刷出了合法分数与产物。门禁的 docstring 明确写下这条不变量：

> `run_success` is a hard precondition: a run that exits non-zero (crash, OOM, timeout) must never be promoted even if it flushed a valid score and artifacts to disk before dying.

配套还堵住了一个隐蔽的连带 bug：**失败的父节点不得锚定晋升基线**。一个崩溃的父节点（即便死前刷了高分）不是真正的 best-so-far，其分数被视为缺失——否则一个崩溃的高分会静默压制掉真正成功的后继。

同时把 GPU 远程 Python 改为 `-u` 无缓冲执行，确保 `CV_SCORE=` 行在进程被杀前已逐行刷出、不随块缓冲丢失。新增两条回归测试（门禁级 + 循环级）复刻 tps-may-2022 场景锁定此行为。

### 创新四：可观测的修复闭环

**根因诊断。** 见失败模式 C——蒙着眼的修复。

**自研修复。**
- 新增 `_clean_error_for_feedback`：剥离 `%|` / `it/s]` / `kB/s]` 等进度帧，保留真实 traceback。
- 失败时把清洗后的**完整报错**落盘到 `EXP###/run_error.txt`（事后可诊断）。
- 把清洗后的完整报错（而非 120 字符摘要）喂回 Diff 修复提示。
- 堵住三处噪声泄漏源（NOTES 注入、cv_history note、记忆 `what_failed`），进度条噪声不再进入任何提示或记忆库。新增回归测试锁定"落盘 + 真报错进提示"。

### 落地后的三处深审修复

把选点大脑接入循环后，我又做了一轮"作为大脑不能出 bug"的深度审计，用离线 trace 逐步复现，发现并修复了三个测试当时漏掉的真实缺陷（其一即失败模式 D）：

1. **全局停滞早退杀死 MCGS**：修复为早退**仅在线性模式生效**；MCGS 开启时跑满预算去融合。去齿验证：还原修复后 MCGS 在第 5 步被杀（`5≠6`）。
2. **单分支自举死锁**：即创新二。
3. **`_ancestors_in_branch` 缺环路保护**：`_depth` 有 `seen` 环路守卫、它没有。当前图不可能成环，但 `export_json` 已在、未来加载图可能引入环，无守卫会让大脑死循环挂起。补齐守卫（对抗性成环图验证：3 秒内返回、不挂起）。

## 六、真实 GPU 验证

本章的立场与 XCIENTIST 一致：**不只看最终工件，还要看搜索、晋升与修复过程本身是否可归因、可检查**。以下结果全部来自真实 A40 GPU（job 87907，Opus 4.8 全程），经"代理进容器"通路（Clash 7890 → SSHPiper 网关 → 容器）接入。这是 MCGS 选点大脑**首次在真实硬件上运行**（此前仅离线）。

### 6.1 多分支自举在 GPU 上真实触发并收敛到最优（8 迭代轮）

在 nomad2018（双目标回归，RMSLE 越低越好，2400 行）上跑通 `--mcgs`：

```
EXP000 Base/primary            cv=0.059770  晋升(基线)
EXP001 Base/primary            cv=0.059516  晋升
EXP002 Base/primary            cv=0.059708  保留   ┐ branch A
EXP003 Stepwise/intra_branch   cv=0.059711  保留   ┘ (停滞)
EXP004 Base/primary(DIVERSIFY) cv=0.058864  晋升   ┐ branch B(从 EXP001 另开)
EXP005 Stepwise/primary        cv=0.058816  保留(Δ<min_delta) │
EXP006 Diff/intra_branch       cv=0.058732  晋升(最佳)        │
EXP007 Diff/intra_branch       cv=0.058728  保留(Δ=4e-6<1e-4) ┘
最佳=EXP006 cv=0.058732   晋升 4/8   基线→最佳 −1.74%
```

**这段轨迹证明的（诚实分级）：**
- ✅ **选点大脑真实驱动**：`intra_branch` 只可能来自 selector，线性模式永不产生；模式序列 Base→Stepwise→Diff 吻合 phase 逻辑而非线性 `_decide_mode`。
- ✅ **多分支在 GPU 上真实分叉并收敛到最优**：EXP001 有两个孩子（EXP002 与 EXP004）= 真实分叉。EXP004 在 balanced 阶段却是 `Base`——只有本计划修的 **DIVERSIFY 路径**会在此产出 `Base`（fallback primary 此时给 Stepwise）。即 branch A 停滞两次触发自举、从最优 EXP001 另开 branch B，而 **branch B 产出了全局最佳解**。创新二不仅在 GPU 上生效，它开出的分支还收敛到了全局最优。
- ✅ **晋升门禁在 GPU 上精确**：拒 EXP002（更差）、EXP007（Δ=4e-6<1e-4）、EXP005（<阈值）。
- ✅ **真实领域思考、非样板**：EXP006 推理"spacegroup 是晶体学类别量（仅约 6 个值）当前被当浮点喂入，独热能给树干净的对称群信号"——真实材料学洞见。最佳解含 LGBM/CatBoost/XGB 三族 + 3-单纯形 OOF 融合权重搜索。

### 6.2 四种扩展全部触发，融合产出全局最优解（12 迭代轮）

另一轮 12 迭代里，**四种 expansion 全部在 GPU 触发**：`primary×4 / cross_branch×4 / aggregation×3 / intra_branch×1`。拓扑在 EXP000 处分叉。而 **`aggregation`（融合）产出了该轮全局最佳解** EXP006（cv=0.05885，晋升），其 hypothesis 明确是"融合共享的 lattice 几何 + spacegroup 独热特征工程 + 三模型 per-target OOF 融合权重 + 多种子平均"——真的把多分支顶尖方案融为一体。

至此**两大能力都在 GPU 上各自产出过全局最优解**：diversify 在 8 迭代轮里收敛到最优、aggregation 在 12 迭代轮里收敛到最优。

### 6.3 四处修复全部在真实 GPU 复验

| 修复 | GPU 复验证据 |
|---|---|
| 门禁（创新三） | EXP004/EXP011 `run_success=False` 被正确挡下、不晋升 |
| 观测（创新四） | 两者 `run_error.txt` 落盘的是**真错**——一条 `EOFError` 瞬时断连、一条 `from scipy_stub import ...` 坏 import，均非进度条噪声 |
| 自举 diversify（创新二） | 8 迭代轮触发并收敛到最优（见 6.1） |
| 停滞不早退（深审修复 1） | 12 迭代轮全局停滞下仍跑满 12 轮；旧线性 bug 会中途早退 |

**容错也在 GPU 验证**：另一轮 5 迭代里 EXP005 的 LLM 生成失败（无代码块），循环优雅 `continue` 跳过、不崩任务。

### 6.4 跨模态机制验证（引擎不只做表格）

引擎已在 5 种问题类型上跑通，证明这套机制不绑定表格：

| 任务 | 模态 | 类型 | 指标 | 最佳 CV |
|---|---|---|---|---|
| nomad2018 | 表格 | 回归(双目标) | RMSLE↓ | 0.0597 |
| tps-may-2022 | 表格 | 二分类 | ROC AUC↑ | 0.9934 |

### 6.5 诚实的范围声明与评测轴的选择

这些是**单任务小数据（nomad2018，2400 行）的机制正确性验证**，证明选点大脑各路径在真实 GPU 上可用、且产出真实解。在此之上，系统已能在数据规模适中的比赛上**独立走完完整研究闭环**——读取任务、分析数据、生成代码、运行实验、按结果继续优化。**跨多任务的稳定增益与经验可迁移性仍需更大规模批量实证**。CV 是本地 proxy，官方分数仍需人工提交确认（Human Gate）。

**交付形态与算力的现实。** 系统以**终端式工具**交付：可通过 npm / pip 全局安装，在本地初始化后配置自有大模型 API、Kaggle API，并可选择接入远程算力服务器——不接则默认用本地算力。底层运行的就是这个 AI Scientist Agent（实验搜索、假设生成、失败归因、记忆经验积累、自动报告），前端面板保留为辅助 dashboard，展示实验进度、搜索树、日志、分数变化与经验总结。也正因为目前主要只有单张 A40、而 MLE-bench 大数据任务的下载与并行训练成本很高（详见第十节），本计划在这一阶段有意把验证聚焦在中小规模、可复现的任务上。

**为什么本计划不以"排行榜名次"作为评测轴。** MLE-bench 全量竞赛套件涉及的数据体量极大，单张 A40 难以在可接受时间内对整套任务完成大规模训练与反复搜索。因此本计划**有意不把竞赛排行榜名次设为主张目标**——在现有算力下，用少量任务的排名去代表系统整体能力，既不可靠也不诚实。我下载了 MLE-bench 的多数竞赛，仅作为**驱动与压测机制的任务基质**（检验选点／晋升／修复在不同数据分布与模态下是否仍然可用），而不是用来宣称榜单成绩。

**本计划真正主张、且已被验证的，是机制层面的事实**：四条选点路径在真实 A40 上可用、diversify 与 aggregation 各自产出过全局最佳解、四处修复都改变了真实搜索行为、每一步判断都留有可检查工件。规模化的稳定增益与官方分数是下一阶段的工作。本计划**明确禁止**用少量任务结果宣称大规模套件上的稳定水平或排行榜成绩——这既是诚信要求，也由系统的 `benchmark_claim_gate` 强制。

## 七、讨论

**这套工作真正的贡献不在"多跑通了几个任务"，而在把三类判断变成可审计的过程。** 一个自动化研究系统如果只交付最终工件，它的可信度就完全依赖于"结果碰巧对"。而当选点计划、晋升裁决、清洗后的报错、validation/claim 审计都被持久化成可检查的工件时，一次错误的判断可以被**定位到具体的一步**，而不是淹没在一次性脚本里。这与 XCIENTIST 的主张一致：AI 科学家应当被评估的，不只是它的最终产物，还有它的合成与验证过程是否可归因、可检查、在科学上可追责。

**四种失败模式的共性值得强调。** 它们无一例外都源于"把本该显式的判断留给了隐式默认"。false promotion 源于门禁默认相信"有产物就是成功"；unreachable fusion 源于扩展规则默认"分支会自己长出来"；blind repair 源于反馈默认"note 前 120 字符就够"；早退源于停滞默认"停滞就该停"。把每一个默认改成一条**有契约、可测试、可在 GPU 上复验**的显式规则，是这套工作的方法论内核。

**诚实的边界。** 我不宣称这套引擎已经在大规模竞赛套件上取得稳定成绩——受限于单张 A40 的算力，对 MLE-bench 全量任务做大规模训练与反复搜索并不现实，本计划也就不把排行榜名次设为主张目标。我宣称的是：在真实 A40 GPU 上，选点大脑的四条路径都可用、diversify 与 aggregation 各自产出过全局最佳解、四处修复都改变了真实搜索行为。机制的正确性已被证明；规模化的稳定增益是下一步。把这两件事分开说，本身就是本计划所主张的"可审计"的一部分。

## 八、与 MLEvolve 的关系：移植边界与自研声明

诚信地界定"什么是移植、什么是自研"，是本计划的一部分。

**移植的是设计思想，不是代码。** 我从 MLEvolve 吸收的是：渐进式 MCGS、四种扩展类型、分支/全局停滞检测、Base/Stepwise/Diff 编码模式、回顾式记忆、提交质量门禁这些**思路**。

**自研的是正确实现、诊断与修复。** 具体而言：

| 维度 | MLEvolve 原状 | 本计划的自研贡献 |
|---|---|---|
| UCT 选点 | `visit_count` 从不自增、方向算反、零测试、**不可用** | 方向正确、backpropagate 真正自增、9 条测试的独立 `mcgs_selector.py` |
| 多分支自举 | 单任务塌成深链、融合够不到（死代码） | DIVERSIFY 主动开分支破死锁，GPU 上开出的分支收敛到全局最优 |
| 晋升门禁 | 只看"分数+产物"，误晋升失败运行 | `run_success` 硬前置 + 失败父节点不锚定基线 |
| 失败修复 | 120 字符摘要、进度条噪声淹没 traceback | 清洗进度帧 + 完整报错落盘 + 真错误进提示 |
| 搜索图耦合 | 直接 import 会引入第二个 `SearchGraph` 名字冲突 | 只读工作站自己的图、私有 side-table、审计 schema 零改动 |

**主流程不可被绕过。** MLEvolve 被克隆到 `external-projects/MLEvolve` 仅用于工程逆向与协议移植；训练、提交、报告仍必须由工作站主流程发起，产生 run id、agent trace、artifact manifest、Gate 与 claim audit。禁止直接训练/提交绕过工作站，禁止把本地 CV 写成官方排名，禁止用少量任务宣称大规模套件上的稳定水平，禁止失败任务缺席 benchmark gap report。

## 九、方法（实现要点）

**解题脚本契约。** 生成的脚本必须：接受 `--data-dir`/`--out-dir`；做 K 折 CV；打印 `CV_SCORE=<float>`；写 `submission.csv` + `metrics.json`；库白名单模态感知（表格禁 torch）；4 分钟内跑完；超 20 万行则采样到约 15 万行。

**双后端 LLM（`llm_client.py`）。** Opus 4.8 主 + DeepSeek 兜底，stdlib-only（GPU 上也能跑），故障自动切换，不泄密，带 User-Agent 绕过 Cloudflare 1010。

**统一入口。**
```bash
# 单任务 GPU
python scripts/run_evolution.py --task-config configs/evolution/nomad2018.json --runner gpu --iterations 3
# 启用 MCGS 选点大脑
python scripts/run_evolution.py --task-config configs/evolution/nomad2018.json --runner gpu --iterations 6 --mcgs
# 批量 GPU，产出 leaderboard
python scripts/run_evolution_batch.py --config-dir configs/evolution --runner gpu --iterations 2
```

**测试规模。** `mcgs_selector` 9 条选点级 + `evolution_engine` 28 条循环级，共 **37 条离线确定性测试**，覆盖门禁/观测/瞬时重试/选点驱动/停滞不早退/冷启动到达多分支/diversify 桥/封顶。

**凭据与安全。** 全部凭据走 `.env`（gitignored）+ env/`*_FILE` 机制，不硬编码；LLM key 的 `repr` 不泄露；GPU 文件只放 `~/jinghw/scripts/gpu_tra/`。

## 十、已知限制与下一步

1. **算力、存储与数据获取的现实约束**：本计划目前主要只有单张 A40。而 MLE-bench 中相当一部分竞赛数据体量极大——尤其是图像、视频、多模态任务，个别数据集可达数百 GB；官方也说明完整准备 MLE-bench 数据本身就需要较长时间（可能两天左右）。在这种条件下，完整下载全部数据并做并行多轮训练并不现实。此外我在实际下载中发现，部分 Kaggle 历史竞赛数据已过期或下架，即便用 Kaggle API 也会出现 404 或无法访问。**需要明确区分的是：这是算力、存储、下载时间与数据源失效带来的约束，而非系统逻辑跑不通**——系统本身已验证可以独立完成数据规模适中的比赛的**完整研究闭环**（读取任务→分析数据→生成代码→运行实验→按结果继续优化）。因此本计划**有意先把能力验证聚焦在可复现、可下载、数据规模适中的任务上**，证明 AI Scientist 的研究闭环成立；待有更稳定的算力与数据缓存环境，再扩展到更大规模的 MLE-bench 任务。
2. **评测轴的选择（与上一条互为因果）**：正因上述约束，本计划不以排行榜名次为主张目标，改以**研究过程质量**（假设合理性、实验设计有效性、失败归因准确性、经验复用、方法进化）、机制正确性与跨任务 proxy 增益为评测轴；下载的 MLE-bench 竞赛仅作驱动/压测机制的任务基质。更大算力下的规模化排行榜实证是后续工作。
3. **面向可复现的工程化措施（进行中）**：为让评估过程更工程化、更可复现，计划在系统内加入**任务数据可用性检测**（下载前探测数据源是否 404/下架）、**数据缓存**（避免重复下载、支持断点续传）、**任务版本管理**、以及**不可用任务显式标记**（把失效任务从评测集中标注剔除，而非让它污染结果）。这样可用任务与不可用任务边界清晰，评测集本身可复现。
4. **规模化**：目前逐任务；需批量循环一批就绪数据集，用多任务实证跨任务稳定增益与经验复用是否真的在起作用。
5. **缓存**：LT4Net 中转不透传 Anthropic 原生缓存（`cache_read` 恒 0）；省钱可切 DeepSeek。
6. **旧轨道漂移**：`scripts/mlebench_closed_loop_pipeline.py` 仍内联 `.v1` 契约，应改为 import `research_os` 消除双份。
7. **图像/文本 torch 方案**：生成器可尝试，但 torch 类方案的 GPU 稳定性仍需更多验证。
8. **Human Gate → Kaggle**：官方分数仍需人工确认后提交（遵守规则）。

## 十一、评测标准

本计划把评测轴放在"研究过程的质量"，而不是单一的最终名次。分为两组：

**A. 研究过程质量（AI Scientist 的核心评价对象）**
- **假设合理性**：每一步扩展是否有据（领域洞见 / CV 历史 / 记忆），而非随机试。
- **实验设计有效性**：CV 与验证集设计是否与任务匹配，能否真正把假设证伪。
- **失败归因准确性**：喂回修复的是不是真 traceback（而非进度条噪声），归因是否指向根因。
- **经验复用**：先前任务的教训是否被后续实验真正调用（跨任务记忆注入，已有测试锁定）。
- **方法进化**：能否从简单调参，逐步走向任务针对性的验证集/loss/数据增强/后处理/伪标签/ensemble。

**B. 机制与工程（支撑上述过程可信的基础）**
- **机制正确性**：选点/晋升/修复的每个判断是否有可检查工件、是否有测试锁定、是否在 GPU 上复验。（已达成）
- **过程可审计性**：能否把一次错误判断定位到具体一步（validation/claim 审计、run_error、晋升 reason）。（已达成）
- **研究闭环成立性**：能否在数据规模适中的任务上，独立走完"读题→分析→生成→运行→按结果优化"的完整循环。（已在中小规模任务上达成）
- **跨任务稳定增益**：在一批就绪数据集的批量循环上，MCGS 是否稳定优于线性基线、经验是否可迁移。（下一阶段）
- **可复现性**：相同配置下 CV 与晋升裁决是否可复现；数据/代码/参数/产物是否留痕；不可用任务是否被显式标记剔除。（本地已达成，官方待人工提交）
