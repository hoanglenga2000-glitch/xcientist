# 科研 Agent 工作站详细建设计划

## 一、任务定位

本计划的目标，是把我现有的 AI 工作站能力整合成一个面向科研数据任务的 Agent 系统，用来辅助完成 Kaggle 数据竞赛、科研案例分析、模型训练、实验记录和结果报告。

这个方向不是简单做一个聊天式 AI 助手，也不是从零训练一个大模型，而是建设一个能真实执行数据科学流程的工作站：给定一个数据任务后，系统能够理解任务、分析数据、生成代码、训练模型、检查结果、记录实验，并形成可复盘的报告。

第一阶段的重点不是追求完全自动化，而是先做出一个可控、可复现、可检查的原型。只要它能稳定跑通一个真实数据任务闭环，就具备继续扩展的基础。

## 二、相关材料带来的启发

这次参考的方向主要包括 AutoKaggle、Agent K、Kaggle competitions 和 AutoResearch AI。

AutoKaggle 的核心启发是：Kaggle 数据竞赛不能只靠一个模型一次性完成，而要拆成阶段化流程。它把任务分成背景理解、初步 EDA、数据清洗、深度 EDA、特征工程、建模验证和预测，并设置 Reader、Planner、Developer、Reviewer、Summarizer 等角色。这说明一个可用的 Kaggle Agent 必须具备分工、执行、调试、检查和总结能力。

Agent K 的核心启发是：更强的 Kaggle Agent 会先生成 scaffold，也就是解题脚手架，再进入后续迭代。它还把任务 ID、数据路径、时间预算、GPU 设备、leaderboard 和最终 submission 都纳入系统。这说明科研 Agent 不只是写代码，而是要管理环境、数据、模型、提交和评测。

AutoResearch AI 的核心启发是：科研自动化不能只追求“自动完成”，还要重视证据保存、可复现性、来源追踪、人工监督和结果责任。否则即使系统跑出结果，也很难成为可靠的科研过程。

因此，我的方案不是直接复刻某一个已有系统，而是吸收它们的核心设计，先做一个适合当前条件的轻量版科研 Agent 工作站。

## 三、为什么先做轻量版

AutoKaggle 的流程清晰，强调代码执行、单元测试和报告生成，但它主要面向表格类 Kaggle 任务，结果也不是百分百成功。因此第一阶段不应该承诺“全自动完成比赛”，而应该先保证完整流程能稳定运行。

Agent K 能力更强，但部署要求较高，包括 Kaggle API、登录信息、浏览器驱动、原始数据目录、多环境配置、时间预算和 GPU 设置。第一阶段如果直接完整复刻，容易把主要精力耗在环境和依赖上。

所以更合适的路线是：先做轻量版原型，跑通表格类数据任务；再逐步加入 scaffold、多轮改进、GPU 训练、leaderboard 记录和更复杂的数据类型。

## 四、总体建设思路

整体思路是以真实任务驱动系统建设。先选择一个表格类 Kaggle 比赛或一个真实科研数据案例作为测试任务，再围绕这个任务搭建完整流程。

系统采用“阶段化工作流 + 工具执行 + 实验记录 + 人工审核”的模式。Agent 负责重复性和工程性工作，例如读取数据、生成代码、训练模型、检查 submission、整理日志和生成报告；人工负责确认研究目标、判断结果价值和决定下一轮改进方向。

这样做的好处是，系统既能提高效率，又不会把科研判断完全交给自动化流程。

## 五、我的工程落地能力体现

这个计划的重点不只是理解文献，而是把文献中的思路落到可运行系统里。我的优势在于已经有 AI 工作站的实际使用经验，可以把 Codex/Claude Code、本地开发环境、GPU 服务器、数据目录、实验日志和报告生成串成一个完整工作流。

在具体实现上，我会优先做能运行、能检查、能复现的功能，而不是只写概念方案。第一版系统会先支持 Kaggle 常见的 `overview.txt`、`train.csv`、`test.csv`、`sample_submission.csv` 输入结构，并完成 baseline、submission 检查和实验报告生成。

后续接入 GPU 时，也不会把 GPU 当作展示点，而是用于真正需要算力的部分，例如深度模型训练、超参数搜索、大规模特征处理和批量实验。这样可以体现系统的工程价值，而不是停留在 AI 工具使用层面。

## 六、工作流设计

### 1. 任务理解

系统先读取任务说明，包括 overview、data description、评价指标、文件结构和 sample submission。

这一阶段要输出结构化任务说明，明确任务类型、目标变量、输入文件、输出文件、评价指标、提交格式和主要风险点。

如果目标列、评价指标或提交格式不清楚，系统应先标记问题，而不是直接进入建模。

### 2. 初步数据分析

系统读取 train.csv、test.csv 和 sample_submission.csv，检查数据规模、字段类型、缺失值、重复值、类别分布、数值分布和训练测试差异。

这一阶段的目的不是只生成描述统计，而是为后续清洗、特征工程和建模提供依据。

### 3. 数据清洗

系统根据数据分析结果执行基础清洗，包括缺失值处理、重复值处理、异常值检查、日期字段格式化、类别字段处理和无效字段识别。

每个清洗动作都要记录原因，避免随意删除字段或制造数据泄漏。第一版以稳健、可解释、可回滚为主。

### 4. 深度数据分析

在基础清洗后，系统进一步分析特征与目标变量的关系，检查高相关字段、类别字段影响、数值字段分布、潜在数据泄漏和训练测试分布偏移。

这一阶段主要服务于特征工程和模型选择。

### 5. 特征工程

第一版只做稳定、可解释的特征处理，例如 one-hot encoding、frequency encoding、数值缩放、日期拆分、简单交叉特征和低方差字段删除。

不一开始加入过度复杂的自动特征工程。原因是复杂特征工具虽然可能提高上限，但也会增加调试难度。第一阶段应优先保证流程稳定。

### 6. 建模与验证

系统先训练 baseline 模型，再逐步加入 RandomForest、LightGBM、XGBoost、CatBoost、神经网络或 GPU 加速模型。

验证方式必须和比赛指标一致。每次实验都要记录模型名称、参数、训练时间、验证指标、输出文件、失败原因和下一步建议。

### 7. Submission 检查

系统生成 submission.csv 后，需要和 sample_submission.csv 对齐检查。

检查内容包括：行数是否一致、列名是否一致、预测列是否缺失、预测值类型是否合理、是否出现 NaN、是否存在明显越界值。

只有通过本地检查的 submission 才进入提交或汇报阶段。

### 8. 报告与复盘

每次运行结束后，系统生成实验报告。报告内容包括任务背景、数据情况、处理方法、模型结果、submission 检查、错误记录、当前不足和下一步计划。

报告必须基于真实输出文件，关键结论要能追溯到数据、日志、模型指标或代码结果。

## 七、系统模块

系统计划拆成六个核心模块。

任务理解模块：读取任务说明，整理目标、指标、文件结构和提交要求。

数据分析模块：完成 EDA、字段检查、缺失值分析、异常分析和训练测试差异分析。

代码执行模块：生成、运行和调试数据处理与建模代码。

模型训练模块：完成 baseline、传统机器学习模型、深度模型和 GPU 加速实验。

实验记录模块：保存每一次运行的参数、指标、日志、输出文件和失败原因。

报告生成模块：生成可阅读的实验报告和阶段复盘。

## 八、实施步骤

第一步，整理当前工作站环境，明确本地电脑、Codex/Claude Code、GPU 服务器、数据目录、实验目录和报告目录分别承担什么功能。

第二步，按照 AutoKaggle 的输入格式准备第一个任务目录，包括 overview.txt、train.csv、test.csv、sample_submission.csv。

第三步，选择一个简单表格类 Kaggle 比赛作为测试任务。优先选择 Titanic 或 House Prices，因为它们数据结构清楚，适合验证完整流程。

第四步，跑通最小闭环：任务理解、EDA、baseline、submission 生成、submission 检查、实验日志和报告。

第五步，加入阶段化流程，把任务拆成背景理解、初步 EDA、数据清洗、深度 EDA、特征工程、建模验证和报告总结。

第六步，加入 scaffold 机制。每次任务开始时，系统先生成解题脚手架，包括指标、验证方案、模型路线、风险点、时间预算和预期输出。

第七步，加入 post-scaffold 改进机制。系统根据验证分数、错误日志和 submission 检查结果，提出下一轮改进方案。

第八步，接入 GPU 服务器。GPU 只用于真正需要算力的部分，例如深度模型、超参数搜索、大规模特征处理和批量实验。

第九步，用第二个任务验证系统是否能迁移。如果系统只能跑通第一个任务，说明只是一次性脚本；如果能迁移到第二个任务，才说明它有工作站价值。

## 九、阶段成果

短期成果：完成一个表格类 Kaggle 任务闭环，包括任务说明、数据分析、baseline 模型、submission 文件、实验日志和报告。

中期成果：形成轻量版科研 Agent 原型，支持阶段化工作流、代码执行、单元测试、提交检查、实验记录和报告生成。

长期成果：扩展成可服务 Kaggle 比赛和科研数据案例的 AI Data Scientist 工作站，能够积累经验、复用流程、持续改进，并逐步支持更复杂的数据任务。

## 十、评测标准

第一，完成率。系统是否能生成 submission 文件，是否能通过本地格式检查，是否能完成完整流程。

第二，有效性。模型验证指标是否合理，是否与比赛评价指标一致，是否能在 leaderboard 或本地验证中取得可比较结果。

第三，可复现性。相同数据、相同配置下是否能复现实验结果，是否保存了数据版本、代码版本、参数和输出文件。

第四，科研可用性。系统是否能生成清晰报告，是否能解释每一步操作，是否能记录失败原因，是否能为下一轮实验提供依据。

## 十一、需要重点改进的地方

第一，把 AutoKaggle 的阶段化流程吸收到系统设计里。

第二，把 Agent K 的 scaffold 和 post-scaffold 思路变成轻量版机制。

第三，把 AutoResearch AI 强调的证据保存、来源追踪和可复现性写入实验规范。

第四，先从表格类 Kaggle 任务开始，避免第一阶段目标过大。

第五，把 GPU 放在真正需要算力的实验中，而不是作为展示点。

第六，把失败记录下来，让失败成为下一轮改进的输入。

## 十二、总结

我的计划是把现有 AI 工作站建设成一个面向 Kaggle 和科研数据任务的 Agent 系统。这个系统参考 AutoKaggle 的多 Agent 分工和阶段化流程，参考 Agent K 的 scaffold + post-scaffold 改进机制，也吸收 AutoResearch AI 对可复现、证据保存和人工监督的要求。

第一阶段先选择一个表格类 Kaggle 比赛或真实数据案例，跑通任务理解、数据分析、baseline 建模、submission 检查、实验记录和报告生成。这个阶段不追求完全自动化，而是先保证系统能真实完成任务、能复现结果、能记录失败原因。

后续逐步加入特征工程、模型对比、GPU 加速、自动调试和多轮改进，让它从一个可控原型发展成可以服务科研数据任务的 AI Data Scientist 工作站。
