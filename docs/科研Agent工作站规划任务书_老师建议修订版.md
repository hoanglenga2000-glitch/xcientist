# 科研 Agent 工作站规划任务书（老师建议修订版）

## 一、修订背景

这份任务书是在原《科研 Agent 工作站详细建设计划》的基础上，根据老师后续修改建议重新整理的版本。

原计划先从 Titanic、House Prices 这类表格 Kaggle 任务做起，主要目的是验证工作站能不能完成任务理解、数据分析、baseline 建模、submission 检查、实验记录和报告生成。这个方向目前已经跑通，说明本地工作站具备了一个最小可复现闭环。

但是老师提醒我，表格类数据只是科研数据任务的一部分。现在的 AutoResearch 系统已经不只覆盖表格数据，还会涉及图像、文本、图结构数据、代码实验、模型训练、论文生成等更完整的科研过程。Kaggle 比赛本身也有各种类型的数据，不应该把工作站长期限定在表格任务上。

所以本次修订的核心变化是：把“表格 Kaggle Agent 原型”重新定位为“AI Data Scientist / AutoResearch 工作站”的第一阶段基础，把后续方向调整为面向多类型数据和完整科研流程的本地可审计工作站。

## 二、老师建议的理解

我理解老师的意思主要有四点。

第一，表格任务可以作为起点，但不能作为终点。Titanic 和 House Prices 适合做基础闭环，因为它们数据结构清楚、指标明确、方便验证。但是如果只停留在表格任务，项目就会显得太窄，不能体现 AutoResearch 系统的完整性。

第二，Kaggle 不是只有表格数据。后续应该从 Kaggle 或公开科研数据中选择图像、文本、图结构等任务，逐步验证工作站能否迁移到更多数据形态。

第三，可以借鉴 AutoSOTA。AutoSOTA 的重点不是简单跑 baseline，而是围绕论文、代码、依赖、实验环境、指标验证和反思改进形成端到端研究循环。它对我后续扩展“复现实验、改进模型、验证结果”很有参考价值。

第四，需要深入看 AutoResearch 相关系统的代码，例如 NanoResearch。老师特别提到，AutoResearch 里面有文献调研、方案设计、代码生成、代码训练、论文生成等环节。如果要做 AI Data Scientist 系统，就应该把这些环节和我现在的工作站结合起来，而不是只做一个数据建模脚本。

## 三、修订后的项目定位

修订后，本项目定位为：建设一个面向科研数据任务的 AI Data Scientist / AutoResearch 工作站。

它不是简单的聊天助手，也不是从零训练一个大模型，而是一个能把科研任务拆解成阶段、调用工具执行实验、保存证据、检查结果、生成报告，并在人工监督下持续改进的本地工作站。

第一阶段已经完成的表格任务闭环，应该被看作“工作站底座”，主要证明系统具备可运行、可复现、可审计的能力。后续要在这个底座上扩展更多数据类型和科研环节。

更准确地说，我后面的方向不是放弃表格任务，而是把它升级为以下路线：

- 用表格 Kaggle 任务验证最小数据科学闭环。
- 用第二类 Kaggle 或科研数据任务验证多数据类型迁移能力。
- 用 AutoResearch / NanoResearch 的阶段思想补齐文献调研、实验方案、代码生成、训练执行、结果分析、图表和论文报告。
- 用 AutoSOTA 的复现与改进思想，逐步加入论文复现实验、模型优化和 validity 检查。
- 用本地 AI 工作站模板，把这些环节组织成可监督、可恢复、可长期维护的 Agent 工作流。

## 四、参考系统带来的启发

### 1. AutoKaggle

AutoKaggle 说明，数据科学任务不能只靠一次性建模完成，而要拆成任务理解、EDA、清洗、特征工程、建模验证、预测提交、调试和总结等阶段。它的多 Agent 分工和 validation 思路已经被我用在当前 Titanic 和 House Prices 双任务闭环中。

对本项目的落地点是：继续保留阶段化 workflow、submission 检查、实验日志、报告和 validation gate。

### 2. Agent K

Agent K 的重点是 scaffold、交互经验、反思和泛化。它说明更强的数据科学 Agent 需要先生成解题脚手架，再基于实验结果进行 post-scaffold 改进，而不是每次都从零开始。

对本项目的落地点是：继续保留 task scaffold、post-scaffold improvement、失败原因记录和经验库规划。

### 3. AutoResearch AI

AutoResearch AI 把科研自动化放在更大的流程中看，包括 literature grounding、hypothesis / planning、experimentation、validation、reporting、revision，以及 novelty、validity、impact、reliability、provenance 等评价维度。

对本项目的落地点是：后续任务书不再只写“完成 Kaggle 建模”，而要写清楚文献依据、实验方案、证据保存、复现命令、人工审核和限制说明。

### 4. AutoSOTA

AutoSOTA 关注从论文到代码、环境、实验、指标验证、反思和改进的端到端研究流程。它的关键价值在于让系统不仅能复现实验，还能在可验证条件下提出改进方向，并用 validity 监督避免虚假提升。

对本项目的落地点是：后续可以增加“论文复现实验任务”，选择有公开代码和可承受算力成本的论文，先完成环境搭建、原结果复现，再做小规模改进和指标验证。

### 5. NanoResearch

NanoResearch 的流程更接近老师说的 AutoResearch 系统：文献检索与假说生成、实验方案设计、环境准备、代码生成、实验执行、结果分析、图表生成、论文撰写、审稿修订。它还强调 manifest、断点恢复、真实实验结果、图表和论文产物。

对本项目的落地点是：我后续应该把当前的 tabular pipeline 扩展成 research pipeline，把“数据任务”继续往“科研实验任务”推进。

### 6. Kaggle 官方 API / CLI

Kaggle CLI 是后续接入官方数据下载、比赛提交、leaderboard 记录的重要工具。但当前本机没有 kaggle.json，也没有配置 Kaggle CLI，因此不能把官方提交写成已完成。

对本项目的落地点是：Kaggle 官方提交属于受控扩展，必须等 token 和 CLI 配置完成后再启用。

## 五、总体建设思路

修订后的建设思路分成两层。

第一层是数据科学执行层。它负责读取数据、分析数据、生成代码、训练模型、检查输出、记录实验和生成报告。当前 Titanic 与 House Prices 已经证明这一层可以运行。

第二层是科研工作流层。它负责文献调研、方案设计、实验矩阵、代码生成、训练执行、结果分析、图表生成、论文报告和审稿修订。这一层是老师希望我后续重点补齐的方向，也是本项目从“表格建模工具”走向“AI Data Scientist 工作站”的关键。

我会采用“先稳底座，再扩范围”的策略。也就是说，不会一开始就承诺支持所有数据类型和完整论文自动生成，而是先把每一阶段做成可验证产物，再逐步扩展。

## 六、工作流设计

修订后的工作流分为九个阶段。

### 1. 任务与文献理解

系统先读取任务说明、数据说明、评价指标和相关文献。对于 Kaggle 任务，重点理解比赛目标、输入输出、sample submission 和 leaderboard 指标。对于科研任务，重点理解研究背景、已有方法、数据来源、研究空白和预期贡献。

这一阶段输出任务说明和文献依据，不能凭空生成引用。

### 2. 实验方案设计

系统根据任务目标生成实验方案，包括数据集、目标变量、评价指标、baseline、候选模型、消融实验、风险点、时间预算和预期产物。

这一阶段要形成 scaffold，相当于先和老师确认“我要怎么做”，再进入代码和训练。

### 3. 数据准备与质量检查

系统检查数据规模、字段类型、缺失值、重复值、异常值、类别分布、训练测试差异和潜在数据泄漏。

如果是图像、文本或图结构数据，后续需要增加对应检查，例如图像尺寸与标签分布、文本长度与类别分布、图节点边关系和划分方式。

### 4. 代码生成与环境准备

系统根据实验方案生成或整理可运行代码，包括数据处理脚本、训练脚本、配置文件、依赖文件和运行命令。

这一阶段要借鉴 AutoSOTA 和 NanoResearch 的做法，把环境、依赖、代码入口和复现命令记录清楚，避免只留下“跑过了”的口头描述。

### 5. 模型训练与实验执行

系统先运行 baseline，再根据任务类型逐步加入更合适的模型。表格任务可以从 sklearn baseline 扩展到 LightGBM、XGBoost、CatBoost；图像任务可以从预训练 CNN / ViT baseline 做起；文本任务可以从 TF-IDF / transformer baseline 做起；图结构任务可以从传统图特征或 GNN baseline 做起。

每次实验必须记录参数、指标、运行时间、输出文件和失败原因。

### 6. 结果分析与有效性检查

系统读取真实实验输出，分析模型效果、错误样本、指标变化和过拟合风险。不能把未运行的结果写成已经完成。

这一阶段要加入 validity 检查，确认指标提升是否来自合理改进，而不是数据泄漏、提交格式错误或偶然波动。

### 7. 图表与证据整理

系统根据真实数据和实验结果生成图表，例如数据分布图、特征重要性、训练曲线、混淆矩阵、模型对比表和消融实验表。

图表必须能追溯到数据文件、日志或模型结果，不能只作为装饰。

### 8. 报告或论文生成

系统生成实验报告。早期以 Markdown / Word 报告为主，后续可以扩展到 LaTeX 论文草稿。

报告内容包括研究背景、数据来源、方法、实验设置、结果、限制、失败记录和下一步计划。如果没有真实实验支撑，只能写成计划或 limitation，不能写成结论。

### 9. 审稿、复盘与下一轮改进

系统对报告和实验产物做检查，包括引用是否真实、指标是否可复现、代码是否可运行、submission 是否合规、限制是否写清楚。

这一阶段输出 post-scaffold 改进建议和下一轮任务计划，形成经验库和失败案例库。

## 七、系统模块规划

系统计划拆成七个核心模块。

任务规划模块：负责理解老师任务、比赛说明、科研背景、评价指标和交付要求。

文献与证据模块：负责检索和保存文献依据、数据来源、引用、实验日志和可复现命令。

数据分析模块：负责表格、图像、文本、图结构等不同数据的基础检查和质量分析。

代码开发模块：负责生成、运行、调试和维护实验代码。

模型训练模块：负责 baseline、模型对比、参数设置、训练执行和指标记录。

报告生成模块：负责生成 Markdown、Word、图表和后续可能的 LaTeX 论文草稿。

审核复盘模块：负责 validation gate、research integrity gate、失败记录、人工确认点和下一轮改进建议。

## 八、实施步骤

### 第一阶段：巩固当前表格任务底座

当前已经完成 Titanic 和 House Prices 双任务闭环。下一步不是重复做同类任务，而是把这部分整理成稳定底座，包括通用 tabular pipeline、validation gate、research integrity gate、Docker dashboard 和可视化验收记录。

阶段成果：稳定可复测的表格数据科学工作站底座。

### 第二阶段：补齐老师建议中的 AutoResearch 规划层

在现有系统上增加更明确的 research workflow 规划，包括文献调研、实验方案设计、代码生成、训练执行、结果分析、图表生成、报告生成和审稿复盘。

阶段成果：形成一份可执行的 research pipeline 设计，不再只描述表格建模。

### 第三阶段：选择第三个真实任务验证迁移

第三个任务不再优先选择简单表格任务，而应优先选择图像、文本或图结构数据任务。如果老师有真实科研数据，就优先使用老师数据；如果暂时没有，就从 Kaggle 或公开数据中选择一个复杂度适中的任务。

阶段成果：证明工作站可以从表格任务迁移到第二类数据形态。

### 第四阶段：引入 AutoSOTA 式论文复现小任务

选择一篇有公开代码、算力要求可控、指标明确的论文，先做环境搭建和原结果复现，再尝试小规模改进。

阶段成果：把工作站从“比赛建模”推进到“科研实验复现与改进”。

### 第五阶段：扩展模型和算力

在本地闭环稳定后，再接入 LightGBM、XGBoost、CatBoost、深度学习模型和 GPU 训练。GPU 不作为展示点，只用于确实需要算力的任务。

阶段成果：形成 CPU baseline 与 GPU 实验的对照记录。

### 第六阶段：建设经验库和失败案例库

把多次任务中的 scaffold、实验日志、错误原因、指标变化和报告复盘整理成可检索经验。

阶段成果：让系统从“每次重新做”变成“会积累项目经验”。

## 九、阶段成果要求

短期成果：完成修订后的任务规划书，明确老师建议如何进入项目路线；保留当前表格闭环作为基础成果。

中期成果：形成 AI Data Scientist 工作站原型，支持任务规划、数据分析、代码执行、训练验证、证据保存、报告生成和复盘改进。

长期成果：逐步扩展到多类型 Kaggle / 科研数据任务，并能够支持文献调研、实验方案、代码生成、训练执行、图表和论文报告，形成可审计、可复现、可长期维护的 AutoResearch 工作站。

## 十、评测标准

第一，任务完成率。系统是否能按照任务要求生成真实可检查的实验产物。

第二，数据类型迁移能力。系统是否能从表格任务迁移到图像、文本或图结构任务。

第三，实验有效性。模型指标是否和评价标准一致，结果是否来自真实运行，是否排除了数据泄漏和虚假提升。

第四，可复现性。是否保存数据来源、配置、代码入口、运行命令、参数、日志和输出文件。

第五，科研可用性。报告是否能说明研究背景、方法、结果、限制和下一步计划，是否适合向老师汇报。

第六，人工监督边界。是否把 Kaggle token、GPU、服务器资源、论文结论和官方 leaderboard 这些关键点放在人工确认后再执行。

## 十一、我需要特别注意的地方

第一，不能把“已经跑通表格任务”说成“已经完成 AutoResearch 系统”。当前成果是底座，不是终点。

第二，后续汇报时要主动说明：老师提醒后，我已经把方向从单纯表格 Kaggle 扩展到多类型数据和完整科研流程。

第三，不要承诺当前已经支持图像、文本、图结构和论文全自动生成。这些应该写成下一阶段扩展任务。

第四，Kaggle 官方下载和 leaderboard 提交必须等 kaggle.json 和 Kaggle CLI 配好后再做，不能伪造。

第五，GPU 和服务器资源要先获得老师或自己明确确认，不能为了展示效果随便接入。

第六，论文或报告里的所有指标、图表、结论都要来自真实实验产物。如果某个环节还没做，就写成 limitation 或 next step。

第七，后续选择第三个任务时，最好不要再选 Titanic / House Prices 这种入门表格任务，而要选一个能体现老师建议的数据类型。

第八，和老师交流时语气要自然，可以说：“老师您提醒后，我理解表格任务只是底座，所以我把任务书重新改成 AI Data Scientist / AutoResearch 工作站路线，后续会按文献调研、方案设计、代码生成、训练执行、结果分析和报告论文这条线继续推进。”

## 十二、总结

修订后，我的项目不再只是一个表格 Kaggle 自动建模脚本，而是一个从表格闭环起步、逐步扩展到多类型数据和完整科研流程的 AI Data Scientist / AutoResearch 工作站。

当前 Titanic 和 House Prices 的结果证明，本地系统已经具备基础执行能力。下一步要按照老师建议，把 AutoResearch、AutoSOTA 和 NanoResearch 中的文献调研、实验方案、代码生成、训练执行、结果分析、图表生成、论文报告和审稿修订吸收进规划中。

我会先保持本地可审计、可复现、可人工监督的原则，不急着承诺全自动科研，而是把每一个阶段都做成真实可检查的产物。这样后续无论接 Kaggle 官方 API、GPU 服务器，还是老师真实科研数据，都有稳定的工作站基础。
